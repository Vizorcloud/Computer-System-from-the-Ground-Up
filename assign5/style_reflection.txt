2. To verify the padding behavior of my printf implementation, I designed tests that checked both space padding and zero padding across multiple format specifiers and widths. For example, I tested %3c to confirm right-aligned space padding ("  M") and continued this testing for all the other formats printf required. I also tested pointer formatting with width ("%12p" → "0x00001234abcd") and truncation cases like snprintf(buf, 5, "%7d", -9999) to confirm padding occurs before truncation. A similar testing strategy would not work well for malloc because padding tests rely on deterministic string output, while memory allocation behavior is non-deterministic by the nature of relating to memory layout. For instance, printing a padded number always produces the same string, but calling malloc(16) twice does not guarantee the same address or layout, so you cannot verify correctness by comparing outputs. Instead, malloc must be tested by checking properties such as whether returned blocks are distinct, properly aligned, reusable after free, and protected against overruns.

Third, it ensures blocks do not overlap existing allocations by comparing address ranges against all active blocks. This catches issues like incorrect splitting or double allocation in the same region. Fourth, verify_payloads() detects payload corruption by filling each block with a predictable byte pattern and rechecking it after every operation. Any unexpected change reveals overwrites. Together, these checks validate that the primary aspects of malloc works such as correct alignment and valid heap bounds and payload isolation/integrity.
